> **Update (same day):** findings 1 and 2 are fixed: fresh records are pushed to

Two layers: local benchmarks of the core, store and replication (release build, no
network; `cargo run --release -p sameroot-sync --example bench 10000`), and live
measurements on the four-node prototype mesh, in a separate `bench` database.

## Local (one ARM64 cloud vCPU class machine, release build)

| Measurement | Result |
|---|---|
| Ledger trie: build 10⁵ / 10⁶ records | 2.1 s / 25.4 s (≈ 40–47k/s) |
| Trie: insert one record into 10⁵ / 10⁶ | 23 µs / 28 µs |
| Trie: inclusion proof at 10⁵ / 10⁶ | 4.9 / 5.6 levels ≈ 656 / 756 B; verify 6–7 µs |
| Logic 1: run the own-subspace preset | 0.17 µs |
| Admission: `verify_entry` (Ed25519 + contract) | 189 µs |
| Store: write value + admit entry (memory or disk) | ≈ 650 µs (≈ 1,500/s) |
| Store: compute the state of 10⁴ entries (cold) | 78 ms |
| Store: read again (cached) | 5 ms |
| Store: **first read after a write** | **83 ms** (the state is recomputed in full) |
| Sync: cold, 10⁴ records to a fresh replica | 6.9 s (≈ 1,440/s); values with them |
| Sync: one new record, after idle | 5.8 ms median |
| Sync: **one new record, writes back to back** | **1.6 s median**, 2.1 s max (roots coalesced to 1/s) |

## Live mesh

Nodes: the hub (cloud), a second cloud server (RTT 3.4 ms), a box behind NAT
(RTT 111 ms), and a laptop on a corporate network through the relay (not measured
directly). Latency is measured with clock timestamps (NTP-synchronised), polling
every 5 ms through the CLI.

| Measurement | Result |
|---|---|
| A write on the hub readable on the server (RTT 3 ms) | 50 ms median, 60 ms max |
| The same on the box (RTT 111 ms) | 647 ms median, 768 ms max |
| Burst: 300 writes through the CLI on the hub | 110 writes/s; both nodes had all 300 by their first poll after the last write |
| 20 × 100 KB values | readable on the server ≈ 1.1 s, on the box ≈ 1.4 s after the last write |
| Catch-up: server offline while 200 records were written | caught up 4.9 s after its service started |
| Restart of the hub service | all three peers back within 16 s (redial interval 15 s) |
| Final state | all nodes at 550 records, the same root |

## Findings

1. **Latency over a long link is about six round trips.** A new record travels
   `root` → `getNodes` per trie level → `want` → `records`, so on a 111 ms link it
   takes ≈ 650 ms. Pushing fresh local records directly to open sessions (an
   unrequested `records` frame, which the receiver already admits) would make it
   ≈ half a round trip.
2. **Back-to-back writes wait for root coalescing** (one root per second): 1.6 s
   median between two local replicas. A shorter window (≈ 100 ms), or the push of
   finding 1, removes it.
3. **The first read after a write recomputes the whole state** (83 ms at 10⁴
   entries, linear). Fine for the prototype; incremental resolution per key is
   needed before large memories.
4. **Ingest is bound by per-record store transactions** (≈ 1,500 records/s, two
   commits each). Batching a received frame into one transaction would raise cold
   sync speed severalfold.
5. Trie, proofs, Logic 1 and admission are far from being bottlenecks.
